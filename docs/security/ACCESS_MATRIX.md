# מטריצת הרשאות (SEC-001)

**מקור האמת:** `firestore.rules` (נבדק בקוד, 30.10.2026). **בדיקות:** `tests/rules/rules.test.ts` רצות מול Firestore Emulator ב-CI בכל פרסום (59 בדיקות Allow/Deny אחרי SEC-002). בסביבת העבודה המקומית האמולטור לא נטען (הורדה חסומה), לכן התוצאות נלקחות מדו"ח ה-CI בענף `ci-reports`.
**חשוב:** הכללים בפרויקטי Firebase מתפרסמים **ידנית** (דניאל) — קוד הכללים במאגר אינו מבטיח שזה מה שרץ בשרת. ראו "סיכון R3" ב-`docs/quality/BASELINE_AUDIT.md`.

## תפקידים
- **מארגן** — `owner` במסמך הטיול.
- **משתתף** — מופיע ב-`members`, אולי משויך למשפחה (`familyId`). אין תפקיד נפרד של "מנהל משפחה" — כל משתתף במשפחה שווה.
- **ממתין** — ביקש להצטרף לטיול סגור (`pending`).
- **משתמש שהוסר** — נמחק מ-`members`; המפתח של המשפחה שלו הוחלף.
- **זר** — מחובר (גם אנונימי) ולא חבר בטיול. **לא מחובר** — בלי אימות.

## ממצאים

|---|---|---|---|---|
| SEC-F1 | ~~**מפתחות ההזמנה של כל המשפחות קריאים לכל משתתף.**~~ `invite.fam.*` במסמך הטיול, וגם `members.*.k`. Firestore מחזיר מסמך שלם — כללים לא מסתירים שדות. משתתף ממשפחה א יכול להעתיק את המפתח של משפחה ב, להצטרף ממכשיר/חשבון נוסף כמשפחה ב — ולקרוא את הציוד הפרטי שלה. | גבוהה (עוקף את הפרדת המשפחות) | גבוהה — נובע ישירות מהכללים ומ[תיעוד Firebase](https://firebase.google.com/docs/firestore/security/rules-fields) | **תוקן 30.10 בקוד (SEC-002)** — המפתחות עברו ל-`trips/{id}/secrets/{all, fam-<id>}` (קריאה: המארגן, ובני אותה משפחה בלבד). מצטרף כותב את המפתח ל-`joins/{uid}` (קריא רק לו) ואז מוסיף את עצמו — הכלל בודק מול הסוד. מיגרציה אוטומטית במכשיר המארגן: המפתחות הקיימים מועתקים כמו שהם (קישורים שנשלחו ממשיכים לעבוד) ורק אחרי אימות נמחקים מהמסמך ומרשומות המשתתפים. אם הכללים בשרת עוד ישנים — נשארת השיטה הקודמת. +12 בדיקות. **בתוקף רק אחרי פרסום כללים.** |
